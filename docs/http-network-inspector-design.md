# HTTP 네트워크 인스펙터 설계

이 문서는 Chrome DevTools의 Network 패널과 비슷한 데스크톱 앱을 설계할 때 필요한 선택과 제약을 설명한다. 앱은 HTTP 통신 기록을 수집하고, 요청과 응답의 헤더, 본문, 타이밍, 실패 원인을 보여준다.

## 먼저 캡처 대상을 정한다

캡처 대상에 따라 구현 방식이 달라진다.

- Chrome 탭만 분석하려면 Chrome DevTools Protocol을 사용한다.
- 브라우저, 명령줄 도구, 데스크톱 앱을 함께 분석하려면 로컬 명시적 프록시를 사용한다.
- 두 범위를 모두 지원하려면 공통 데이터 모델을 두고 캡처 소스를 분리한다. 첫 릴리스에서는 한 소스만 완성한다.

이 프로젝트에는 로컬 프록시를 중심으로 한 설계가 적합하다. 프록시는 Chrome에 종속되지 않으며 여러 HTTP 클라이언트를 다룰 수 있다. 나중에 Chrome DevTools Protocol 수집기를 추가할 수 있도록 내부 경계만 남긴다.

## Chrome DevTools Protocol 방식

앱이 Chrome의 디버깅 인터페이스에 연결하고 `Network` 이벤트를 받는다.

이 방식은 다음 정보를 제공한다.

- 요청을 만든 JavaScript와 initiator
- 브라우저 캐시와 Service Worker 상태
- 브라우저가 측정한 상세 타이밍
- 요청과 응답의 본문
- WebSocket 연결과 프레임

HTTPS 인증서를 가로채지 않아도 본문을 읽을 수 있다는 점이 큰 장점이다. 반면 연결한 Chrome 탭만 관찰할 수 있다. 다른 프로그램의 통신은 볼 수 없다.

Chrome 136부터 기본 사용자 프로필에서는 `--remote-debugging-port`와 `--remote-debugging-pipe`가 적용되지 않는다. 전용 사용자 데이터 디렉터리나 Chrome for Testing을 사용해야 한다. 사용자의 일반 브라우저 프로필에 자동으로 연결하는 기능은 피한다.

## 로컬 프록시 방식

대상 프로그램이 앱의 프록시를 거쳐 서버와 통신한다.

```text
대상 프로그램 -> 127.0.0.1:임시포트 -> 캡처 엔진 -> 실제 서버
```

프록시는 Chrome 외의 프로그램도 지원할 수 있다. 그러나 다음 트래픽은 보장할 수 없다.

- 프록시 설정을 무시하는 프로그램
- 직접 연결하거나 자체 네트워크 스택을 쓰는 프로그램
- VPN이나 별도 프록시 경로를 쓰는 프로그램
- 인증서 고정이나 독립 인증서 저장소를 쓰는 프로그램
- 지원하지 않는 QUIC과 HTTP/3 트래픽

제품 화면은 캡처 범위를 "이 프록시를 경유한 HTTP 통신"으로 표시해야 한다. 앱이 시스템의 모든 트래픽을 수집한다고 표현하면 안 된다.

프록시만으로는 initiator, Service Worker, 브라우저 캐시 상태를 알 수 없다. 이 정보가 핵심 요구사항이면 Chrome DevTools Protocol을 첫 캡처 방식으로 선택한다.

## 권장 구조

```text
┌──────────────── Desktop UI ────────────────┐
│ 세션 제어, 요청 목록, 상세, 검색, 내보내기  │
└──────────────────┬─────────────────────────┘
                   │ 제한된 IPC
┌──────────────────▼─────────────────────────┐
│               Capture Service              │
│ 세션 수명, 설정 검증, 상태 알림             │
├───────────────┬──────────────┬──────────────┤
│ Proxy Engine  │ Exchange     │ Authority    │
│ 연결, TLS     │ 이벤트 조립  │ CA, 신뢰     │
├───────────────┴──────┬───────┴──────────────┤
│                      Store                  │
│ 메타데이터 DB, 본문 파일, 쿼터, HAR         │
└─────────────────────────────────────────────┘
```

### Capture Service

`CaptureService`는 데스크톱 UI가 호출하는 유일한 백엔드 API다. 다음 기능을 제공한다.

- 캡처 세션을 시작하고 중지한다.
- 세션과 캡처 소스의 상태를 반환한다.
- 요청 목록과 상세 정보를 조회한다.
- 큰 본문을 범위 단위로 읽는다.
- HAR 파일을 내보낸다.
- 시스템 프록시 적용과 복원을 조정한다.

UI는 프록시 엔진, 인증서, 데이터베이스 모듈을 직접 호출하지 않는다. 이 제한은 네트워크 정책과 보안 검사를 백엔드 한곳에 둔다.

### Proxy Engine

`ProxyEngine`은 네트워크 전달을 책임진다.

- 루프백 주소에서 연결을 받는다.
- HTTP/1.1 메시지를 파싱한다.
- HTTPS `CONNECT` 터널을 전달한다.
- 사용자가 허용하면 TLS를 복호화한다.
- 업스트림 서버에 연결하고 인증서를 검증한다.
- 요청별 캡처 이벤트를 만든다.
- WebSocket 업그레이드를 전달한다.

기록 저장이 느려져도 네트워크 전달은 가능한 한 계속되어야 한다. 제한된 기록 큐가 가득 차면 엔진은 본문 기록을 생략하거나 잘림 상태를 남긴다. 엔진은 세션별 손실 카운터를 별도 경로로 관리해야 한다. 이벤트 큐가 가득 찼을 때 누락 알림까지 함께 사라지면 안 된다.

### Exchange assembler

`ExchangeAssembler`는 캡처 이벤트를 하나의 HTTP 교환 기록으로 조립한다. 요청은 진행 중, 완료, 실패, 취소, 불완전 상태를 가질 수 있다.

연결이 끊어진 기록도 보관한다. 예를 들어 응답이 없는 기록과 TLS 연결 단계에서 실패한 기록은 서로 다른 상태다. 소스가 종료되면 진행 중인 요청을 불완전 상태로 확정한다.

현재 프록시 엔진은 별도 조립 단계 없이, 요청 시작 시 게시한 `Exchange`의 공유 상태에 결과를 한 번 확정한다. 이유와 상태 목록은 `docs/f12-network-increment-design.md`에 있다.

### Authority

`Authority`는 HTTPS 검사에 사용하는 로컬 인증 기관을 소유한다.

- 로컬 CA를 생성한다.
- CA 개인키를 보호한다.
- 인증서 지문과 신뢰 상태를 반환한다.
- OS 신뢰 저장소에 CA를 설치하고 제거한다.
- 대상 도메인의 임시 서버 인증서를 발급한다.

OS별 어댑터는 설치 명령을 실행할 뿐이다. 인증서 설치 상태와 정책은 `Authority`만 관리한다.

### Store

`Store`는 기록 데이터의 유일한 작성자다.

- SQLite에 세션과 요청 메타데이터를 저장한다.
- 큰 본문은 별도 파일에 저장한다.
- 저장 용량과 보존 기간을 적용한다.
- 필터와 페이지 조회용 인덱스를 관리한다.
- HAR 내보내기 정책을 적용한다.

SQLite에는 `(session_id, started_at, record_id)` 복합 인덱스를 둔다. 큰 본문은 데이터베이스 행에 넣지 않는다. UI는 목록을 먼저 읽고, 사용자가 항목을 선택할 때 상세 정보와 본문을 읽는다.

## 핵심 데이터 모델

불완전한 통신을 정확히 표현할 수 있어야 한다.

```rust
struct Exchange {
	id: RecordId,
	session_id: SessionId,
	source: CaptureSourceKind,
	started_at: Timestamp,
	request: Request,
	outcome: Outcome,
	timing: Timing,
}

struct Request {
	method: Method,
	url: Url,
	headers: Vec<Header>,
	body: BodyState,
}

enum Outcome {
	InFlight,
	Response(Response),
	Failed {
		stage: FailureStage,
		message: String,
	},
	Cancelled,
	Incomplete {
		reason: IncompleteReason,
	},
}

enum BodyState {
	None,
	Stored {
		id: BodyId,
		captured_bytes: u64,
		total_bytes: Option<u64>,
		truncated: bool,
	},
	Omitted {
		reason: OmissionReason,
	},
}
```

데이터 모델은 다음 규칙을 지킨다.

- 헤더는 맵이 아니라 배열로 저장한다. 배열은 중복 헤더와 원래 순서를 보존한다.
- 관측하지 못한 타이밍은 `0`이 아니라 `None`으로 저장한다.
- 응답 없음과 빈 응답을 구분한다.
- 정책, 용량 초과, 과부하, 미지원으로 생긴 본문 누락을 구분한다.
- 목록용 `RecordSummary`와 상세용 `RecordDetail`을 분리한다.
- 같은 URL과 시각을 가진 기록을 자동으로 합치지 않는다.
- 캡처 출처와 소스 내부 요청 ID를 보존한다.

Chrome DevTools Protocol 수집기를 추가해도 wire 형식을 공개 데이터 모델에 노출하지 않는다. 수집기는 외부 이벤트를 검증한 후 공통 도메인 이벤트로 변환한다.

## HTTPS 검사

HTTPS 검사에서는 앱이 두 TLS 연결 사이에 위치한다.

```text
클라이언트 <- 로컬 CA가 서명한 TLS -> 프록시
프록시 <- 정상 TLS 검증 -> 실제 서버
```

클라이언트가 로컬 CA를 신뢰해야 프록시가 내용을 복호화할 수 있다. 이 기능은 다음 정책을 따라야 한다.

- HTTPS 복호화는 기본으로 끈다.
- 사용자가 위험 설명과 인증서 지문을 확인한 후 켠다.
- 앱 설치마다 고유한 CA를 만든다.
- CA 개인키는 OS 자격 증명 저장소나 접근이 제한된 파일에 보관한다.
- 프록시는 업스트림 서버의 인증서와 호스트 이름을 항상 검증한다.
- 인증서 오류를 자동으로 무시하지 않는다.
- CA 제거 기능과 제거 결과를 제공한다.
- 세션 종료와 CA 제거를 별도 작업으로 취급한다.
- 인증서 고정이나 mTLS 실패를 우회하지 않고 실패 원인을 표시한다.

현재 구현은 기본 터널 모드와 사용자가 켜는 HTTP/1.1 복호화 모드를 제공한다. CA 설치와 제거는 아직 자동화하지 않는다. 남은 범위와 완료 조건은 [HTTPS 후속 작업](https-future-work.md)에 정의한다.

## 프로토콜 지원 순서

처음부터 모든 프로토콜을 구현하면 첫 릴리스의 범위가 너무 커진다. 다음 순서로 추가한다.

1. HTTP/1.1
2. HTTPS `CONNECT` 터널
3. HTTPS 복호화
4. WebSocket handshake와 프레임
5. HTTP/2
6. HTTP/3과 QUIC

HTTP/2는 한 연결에서 여러 스트림을 동시에 처리한다. 구현에는 스트림별 상태와 흐름 제어가 필요하다.

HTTP/3은 UDP 기반 QUIC을 사용한다. 일반 TCP 프록시와 같은 경로로 처리할 수 없다. MVP는 HTTP/3을 지원하지 않는다고 표시한다. 개발용 브라우저가 HTTP/2로 연결하도록 QUIC을 끄는 방법도 제공할 수 있다.

## 보안과 개인정보

캡처 데이터에는 암호, 세션 쿠키, JWT, 개인정보가 포함될 수 있다. 다음 정책을 기본값으로 둔다.

- 프록시는 `127.0.0.1`에만 바인딩한다.
- 본문에 요청별, 세션별, 전체 디스크 용량 제한을 둔다.
- `Authorization`, `Cookie`, `Set-Cookie`를 기본으로 가린다.
- 제품 정책이 허용하면 민감 정보는 저장 전에 제거한다.
- 제거된 필드에는 제거 사유를 남긴다.
- HAR 기본 내보내기는 민감 헤더와 본문을 제외한다.
- 캡처한 HTML과 JavaScript를 실행하지 않는다.
- 사용자가 기록 전체를 삭제하고 보존 기간을 설정할 수 있게 한다.
- 검색 인덱스와 진단 로그에 원본 비밀값을 복제하지 않는다.

원본 민감 헤더를 저장할지, 저장 전에 제거할지는 제품 정책으로 확정해야 한다. 화면에서만 가리는 방식은 디스크에 남은 원본을 보호하지 못한다.

## 시스템 프록시 복원

시스템 프록시를 자동으로 바꾸면 설정이 남아서 인터넷 연결을 방해할 수 있다. 다음 흐름으로 변경하고 복원한다.

1. 기존 프록시, PAC, 예외 목록을 저장한다.
2. 앱의 프록시 주소를 적용한다.
3. 종료할 때 현재 설정이 앱이 적용한 값과 같은지 검사한다.
4. 값이 같을 때만 이전 설정을 복원한다.
5. 다른 프로그램이 값을 바꿨다면 덮어쓰지 않고 사용자에게 알린다.
6. 비정상 종료 후 다음 실행에서 복구 상태를 검사한다.

첫 릴리스에서는 시스템 설정을 바꾸지 않는 편이 안전하다. 사용자가 테스트할 프로그램에 프록시 주소를 직접 설정하도록 한다.

## 데스크톱 UI

메인 화면은 Chrome Network 패널과 비슷한 구조를 사용한다.

- 상단에는 캡처 시작, 중지, 현재 소스, 필터, 기록 삭제를 둔다.
- 중앙에는 가상화한 요청 목록을 둔다.
- 오른쪽이나 아래쪽에는 선택한 요청의 상세 정보를 둔다.
- 상세 화면에는 Headers, Payload, Preview, Response, Timing, Cookies, WebSocket 탭을 둔다.
- Waterfall은 각 요청의 시작 시각과 기간을 표시한다.
- 본문 누락, 잘림, 복호화 실패, 저장 과부하를 눈에 띄게 표시한다.

요청 목록에는 다음 열을 우선 제공한다.

```text
Method | Host/Path | Status | Type | Size | Duration | Source | Waterfall
```

응답 미리보기는 신뢰할 수 없는 콘텐츠로 취급한다. HTML을 렌더링해야 한다면 스크립트를 끈 격리 환경을 사용한다. MVP에서는 텍스트와 안전한 이미지 미리보기만 제공하는 편이 낫다.

## 기술 선택

다음 구성이 제품 요구사항과 잘 맞는다.

- 캡처 엔진은 Rust로 작성한다.
- 데스크톱 셸은 Tauri 2를 사용한다.
- UI는 React 또는 Vue와 TypeScript로 작성한다.
- 메타데이터는 SQLite에 저장한다.
- 본문은 파일 기반 blob 저장소에 보관한다.
- UI는 명령형 IPC와 변경 알림 스트림으로 백엔드와 통신한다.
- 기록은 HAR로 내보내고 개별 요청은 cURL로 복사할 수 있게 한다.

캡처 엔진과 UI는 논리적으로 분리한다. UI 렌더링이 느려져도 프록시 전달이 멈추면 안 된다. MVP에서는 같은 프로세스의 별도 작업으로 시작할 수 있다. 안정성 요구가 커지면 캡처 엔진을 별도 프로세스로 옮긴다.

Tauri의 프론트엔드에는 필요한 네이티브 명령만 허용한다. 프론트엔드가 파일 시스템, 프로세스 실행, 인증서 기능을 직접 사용할 수 있게 하면 안 된다.

## 검증 전략

테스트는 내부 구현보다 사용자가 관찰하는 동작을 검사한다.

- 로컬 테스트 서버로 HTTP 요청과 응답을 검증한다.
- 중복 헤더, 큰 본문, 중단된 응답, 동시 요청을 검증한다.
- TLS 인증서 오류와 복호화 거부를 검증한다.
- 느린 저장소와 디스크 용량 초과에서도 네트워크 전달이 지속되는지 확인한다.
- 기록 손실 수와 본문 잘림이 UI에 표시되는지 확인한다.
- 강제 종료 후 시스템 프록시를 안전하게 복구하는지 OS별로 확인한다.
- 저장 중 종료한 뒤에도 본문 참조가 깨지지 않는지 확인한다.
- 기본 HAR 내보내기에 민감한 값이 없는지 검사한다.
- 캡처한 HTML과 JavaScript가 UI에서 실행되지 않는지 검사한다.

Chrome DevTools Protocol 수집기를 추가할 때는 이벤트 순서가 바뀌거나 일부 본문을 읽지 못하는 경우를 fixture로 검증한다. 리디렉션 단계와 대상별 요청 ID 충돌도 별도 사례로 둔다.

## 개발 단계

### 1단계: 안전한 HTTP 프록시

- 루프백 HTTP/1.1 프록시
- 불투명한 `CONNECT` 터널
- 요청 목록과 상세 화면
- 실패 단계 표시
- 수동 프록시 설정
- 메모리 제한과 저장 용량 제한

이 단계의 완료 조건은 HTTP 요청 하나가 프록시를 통과하고 UI에 나타나는 것이다. 앱을 종료해도 네트워크 설정이 바뀌지 않아야 한다.

### 2단계: HTTPS 검사

- 로컬 CA 생성과 제한된 개인키 저장
- 수동 CA 신뢰 설정을 위한 경로와 지문 표시
- 업스트림 TLS 인증서와 호스트 이름 검증
- 민감 헤더 제거와 제한된 본문 미리보기
- CA 설치와 제거 자동화는 후속 작업으로 분리

### 3단계: 제품 기능

- 시스템 프록시 적용과 조건부 복원
- HAR 내보내기
- cURL 복사와 요청 재전송
- 검색, 필터, Waterfall
- 비정상 종료 복구

### 4단계: 프로토콜과 소스 확장

- WebSocket 프레임
- HTTP/2
- Chrome DevTools Protocol 수집기
- 검증된 수요가 있으면 HTTP/3

새 캡처 소스를 추가할 때까지 범용 플러그인 체계를 만들지 않는다. 첫 프록시 경로를 끝까지 구현한 뒤 실제 두 번째 소스의 요구사항으로 공통 경계를 정한다.

## 구현 전에 확정할 항목

다음 결정은 저장 정책과 운영체제 통합 방식에 영향을 준다.

- 첫 릴리스가 지원할 운영체제
- Chrome 전용 분석과 여러 프로그램 분석 중 우선순위
- 원본 민감 헤더를 디스크에 저장할지 여부
- 기본 본문 저장 용량과 보존 기간
- HTTPS 복호화를 첫 릴리스에 포함할지 여부
- WebSocket 프레임이 MVP에 필요한지 여부
- 기업 프록시, PAC, VPN 환경을 지원할지 여부

## 설계 원칙

이 설계는 다음 원칙을 따른다.

1. 앱은 실제로 관측한 범위만 표시한다.
2. 네트워크 전달과 기록 저장을 분리한다.
3. HTTPS 복호화와 민감 정보 저장에는 사용자의 명시적 선택이 필요하다.
4. 데이터 상태는 완료뿐 아니라 실패, 누락, 잘림을 표현한다.
5. 첫 릴리스는 한 캡처 방식을 끝까지 구현한다.
