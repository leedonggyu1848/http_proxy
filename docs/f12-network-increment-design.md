# Network 상세 보기 설계

## 문제

상세 보기 도입 전 프록시는 응답 헤더가 도착하면 메서드, 대상, 상태와 응답 대기 시간만 기록한다. 요청과 응답 본문은 스트리밍으로 전달되므로 이 시점에는 본문이 끝나지 않았을 수 있다. 상세 정보를 추가하면서도 프록시가 본문 전체를 기다리거나 메모리에 모아서는 안 된다.

## 사용자 관점

사용자는 요청 목록을 문자열과 결과 종류로 필터링한다. 행을 선택하면 다음 정보를 확인한다.

- 원본 요청 헤더와 응답 헤더
- 요청과 응답 본문의 미리보기. 일반 본문은 방향별 최대 8KiB이며, 지원하는 이미지 응답은 [별도 한도](guide/body-view.md#이미지-응답-미리보기)를 적용한다.
- 본문 관찰 바이트 수
- 스트리밍 중, 완료 또는 중단 상태
- 미리보기 잘림 또는 관찰 생략 여부

CONNECT 요청은 터널 내부가 암호화되어 있다는 설명만 표시한다. 필터는 기록을 삭제하지 않으며 선택은 안정적인 기록 ID로 유지한다.

## 구조

`Exchange`는 프로세스 안에서 고유한 `RecordId`, 프록시 실행마다 새로 정하는 `SessionId`, 캡처 경로(`CaptureSource`), 요청 도착 벽시계 시각, `CapturedRequest`(메서드, 대상, 요청 헤더, 선택적인 요청 본문 미리보기)를 가진다. HTTP 응답 결과인 `CapturedResponse`에는 상태 코드, HTTP 버전, reason, 응답 헤더와 응답 본문 미리보기가 포함된다.

교환 결과(`Outcome`)는 `InFlight`에서 시작해 다음 중 정확히 하나로 한 번만 확정된다.

- `Response`: 응답 헤더가 도착했다. 이후 본문 진행은 본문 미리보기의 수명 상태로 표현한다.
- `Tunnel`, `InspectionEstablished`: `CONNECT` 터널 또는 HTTPS 검사 세션이 열렸다.
- `Failed`: 응답 헤더 전에 실패했다. 실패 단계(`FailureStage`)를 함께 기록한다.
- `Cancelled`: 클라이언트가 결과 전에 연결을 닫았다.
- `Incomplete`: 결과 전에 프록시가 멈췄다. 열린 터널도 같은 이유로 `TunnelState::Incomplete`가 된다.

`Timing`은 응답을 다음 연속 구간으로 나눈다. 관측하지 못했거나 아직 끝나지 않은 구간은 `0`이 아니라 `None`이다.

- `connect`: 이름 해석과 업스트림 연결(검사 중인 HTTPS는 TLS 핸드셰이크 포함)
- `send`: 요청을 업스트림 연결에 넘긴 때부터 요청 본문이 끝날 때까지
- `wait`: 요청 본문이 끝난 때부터 응답 헤더가 도착할 때까지(TTFB). 서버가 요청 본문이 끝나기 전에 응답하면 `None`이다.
- `receive`: 응답 헤더부터 응답 본문이 끝날 때까지. 완료, 중단, 취소 모두 끝으로 본다.
- `complete`: 요청 시작부터 더 관측할 것이 없을 때까지. 응답은 본문 끝, 다른 결과는 확정 시점이다.

시간은 본문 미리보기가 처음 끝난 순간을 기록해 계산한다. 별도 완료 이벤트를 보내지 않으므로 큐 손실로 시간이 사라지지 않는다.

본문 미리보기는 수명 상태와 보존 상태를 분리한다.

- 수명 상태: `Streaming`, `Complete`, `Interrupted`(보내는 쪽 오류, 예: 업스트림이 본문 도중 연결을 끊음), `Cancelled`(받는 쪽이 읽기를 멈춤, 예: 클라이언트 연결 종료나 프록시 중지)
- 보존 상태: `Prefix`, `Truncated`, `Omitted`

프록시는 Hyper 본문을 `ObservedBody`로 감싼다. 이 래퍼는 원본 본문이 폴링될 때만 같은 프레임을 관찰하고 그대로 전달한다. 별도의 소비 작업을 만들거나 `collect`를 호출하지 않는다. 관찰 데이터 잠금은 기다리지 않으며 경쟁이 발생하면 해당 미리보기를 `Omitted`로 표시한다.

요청이 도착하면 `InFlight` 교환을 기존 제한 채널에 `try_send`로 한 번 게시한다. 이후 엔진은 결과, 연결 시간, 요청 본문 미리보기를 교환이 공유하는 상태에 한 번씩 기록하고, UI는 같은 교환을 읽는다. 따라서 갱신 이벤트가 손실되어 영원히 진행 중으로 보이는 문제가 없고, 응답을 기다리는 요청과 SSE처럼 끝나지 않는 응답도 즉시 목록에 나타난다. 큐가 가득 차서 손실되는 것은 게시 이벤트뿐이며, 그 수는 별도 카운터가 센다.

엔진의 요청 작업이 결과를 확정하지 못한 채 drop되면 교환을 확정한다. 엔진은 런타임을 종료하기 직전에 중지 표시를 세우므로, 그 뒤의 drop은 `Incomplete`, 그 전의 drop은 클라이언트 연결 종료로 인한 `Cancelled`로 기록한다.

헤더는 방향별 최대 64개와 16KiB로 제한한다. `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie` 값은 저장 전에 가린다. 대상은 4KiB, 오류 메시지는 1KiB로 제한한다. 일반 본문 앞부분은 방향별 8KiB까지 보존한다. 지원하는 이미지 응답의 미리보기 한도는 응답당 8MiB, 프로세스 전체 64MiB다. 요청 목록은 최대 2,000건을 유지하며, 기본 게시 대기열의 용량은 512건이다.

## 모듈 소유권

- [`http-inspector-exchange`](../crates/http-inspector-exchange/src/). 공유 캡처 타입, 헤더 마스킹과 미리보기 한도를 관리한다.
- [`http-inspector-core::interception`](../crates/http-inspector-core/src/interception/). HTTP 요청을 전달하고 스트리밍 본문을 관찰하며 캡처 레코드를 게시한다.
- [`http-inspector-analysis`](../crates/http-inspector-analysis/src/). 요청 목록 보관과 필터, 검색, URL 맵 집계를 담당한다.
- [`src/ui/`](../src/ui/). 앱의 선택 상태, 요청 목록과 상세 화면을 관리한다.

Hyper 타입, 잠금과 폴링 구현은 공개 API에 노출하지 않는다. UI만 기록 목록과 선택 상태를 변경한다.

## 대안

요청 시작 이벤트 뒤에 같은 ID로 결과 갱신 이벤트를 보내 UI 쪽에서 조립하는 방식은, 제한 채널이 갱신 이벤트만 버리면 기록이 영원히 `InFlight`로 남아 제외했다. 본문 프레임마다 변경 이벤트를 보내는 방식은 제한 채널에서 시작 또는 종료 이벤트가 손실되면 상태를 복원할 수 없어 제외했다. 본문 종료 후 완성된 기록 하나만 보내는 방식은 SSE와 장시간 다운로드가 목록에 나타나지 않아 제외했다. 본문 전체를 먼저 수집하는 방식은 스트리밍과 메모리 제한을 깨뜨려 제외했다.

## 구현 검증

통합 테스트는 실제 TCP 연결을 사용해 다음 동작을 확인한다.

- 요청과 응답 헤더가 상세 기록에 남는다.
- 민감한 헤더 값은 저장 전에 가려진다.
- 요청과 응답 본문은 변경 없이 전달된다.
- 큰 본문 미리보기는 제한 크기에서 잘리지만 전체 본문은 전달된다.
- 빈 본문, 완료와 중단 상태가 구분된다.
- CONNECT 터널은 계속 양방향으로 동작한다.

## 구현 조정

구현 중 수명과 보존 상태, 공개 접근자 또는 모듈 소유권이 달라지면 이 문서와 테스트 계약을 같은 작업 단위에서 갱신한다.
