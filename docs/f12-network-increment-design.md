# Network 상세 보기 설계

## 문제

현재 프록시는 응답 헤더가 도착하면 메서드, 대상, 상태와 응답 대기 시간만 기록한다. 요청과 응답 본문은 스트리밍으로 전달되므로 이 시점에는 본문이 끝나지 않았을 수 있다. 상세 정보를 추가하면서도 프록시가 본문 전체를 기다리거나 메모리에 모아서는 안 된다.

## 사용자 관점

사용자는 요청 목록을 문자열과 결과 종류로 필터링한다. 행을 선택하면 다음 정보를 확인한다.

- 원본 요청 헤더와 응답 헤더
- 요청과 응답 본문의 최대 8KiB 미리보기
- 본문 관찰 바이트 수
- 스트리밍 중, 완료 또는 중단 상태
- 미리보기 잘림 또는 관찰 생략 여부

CONNECT 요청은 터널 내부가 암호화되어 있다는 설명만 표시한다. 필터는 기록을 삭제하지 않으며 선택은 안정적인 기록 ID로 유지한다.

## 구조

`CaptureRecord`는 프로세스 안에서 고유한 `RecordId`, 요청 헤더와 선택적인 요청 본문 미리보기를 가진다. HTTP 응답 결과에는 응답 헤더와 응답 본문 미리보기가 포함된다.

본문 미리보기는 수명 상태와 보존 상태를 분리한다.

- 수명 상태: `Streaming`, `Complete`, `Interrupted`
- 보존 상태: `Prefix`, `Truncated`, `Omitted`

프록시는 Hyper 본문을 `ObservedBody`로 감싼다. 이 래퍼는 원본 본문이 폴링될 때만 같은 프레임을 관찰하고 그대로 전달한다. 별도의 소비 작업을 만들거나 `collect`를 호출하지 않는다. 관찰 데이터 잠금은 기다리지 않으며 경쟁이 발생하면 해당 미리보기를 `Omitted`로 표시한다.

응답 헤더가 도착하면 기록을 기존 제한 채널에 `try_send`로 한 번 게시한다. UI는 공유 미리보기의 읽기 전용 스냅샷을 조회한다. 따라서 종료 이벤트가 손실되어 영원히 완료되지 않은 것처럼 보이는 문제가 없고, SSE처럼 끝나지 않는 응답도 즉시 목록에 나타난다.

헤더는 방향별 최대 64개와 16KiB로 제한한다. `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie` 값은 저장 전에 가린다. 대상은 4KiB, 오류 메시지는 1KiB로 제한한다. 요청과 응답 본문은 각각 8KiB만 보존한다.

2,000개 UI 기록과 512개 대기 기록이 모든 제한에 도달하면 본문과 헤더 데이터는 객체 오버헤드를 제외하고 최대 약 118MiB를 차지할 수 있다. 진행 중 요청은 각각 최대 약 48KiB를 추가한다. 이 단계에서는 동시 연결 수를 새로 제한하지 않고 모든 단위 제한을 한 모듈에서 관리한다.

## 모듈 소유권

- `domain.rs`: UI가 읽는 기록 ID, 헤더와 본문 스냅샷 타입
- `capture.rs`: 제한 적용과 스트리밍 본문 관찰
- `proxy.rs`: HTTP 경계에서 캡처를 만들고 제한 채널에 게시
- `main.rs`: 기록 보존, 필터, 선택과 상세 화면

Hyper 타입, 잠금과 폴링 구현은 공개 API에 노출하지 않는다. UI만 기록 목록과 선택 상태를 변경한다.

## 대안

본문 프레임마다 변경 이벤트를 보내는 방식은 제한 채널에서 시작 또는 종료 이벤트가 손실되면 상태를 복원할 수 없어 제외했다. 본문 종료 후 완성된 기록 하나만 보내는 방식은 SSE와 장시간 다운로드가 목록에 나타나지 않아 제외했다. 본문 전체를 먼저 수집하는 방식은 스트리밍과 메모리 제한을 깨뜨려 제외했다.

## 구현 검증

통합 테스트는 실제 TCP 연결을 사용해 다음 동작을 확인한다.

- 요청과 응답 헤더가 상세 기록에 남는다.
- 민감한 헤더 값은 저장 전에 가려진다.
- 요청과 응답 본문은 변경 없이 전달된다.
- 큰 본문 미리보기는 제한 크기에서 잘리지만 전체 본문은 전달된다.
- 빈 본문, 완료와 중단 상태가 구분된다.
- CONNECT 터널은 계속 양방향으로 동작한다.

## 구현 조정

구현 중 수명과 보존 상태, 공개 접근자 또는 모듈 소유권이 달라지면 이 문서와 테스트 계약을 같은 작업 단위에서 갱신한다.
