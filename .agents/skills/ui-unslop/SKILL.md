# UI 슬롭 방지

가장 먼저 설명 글을 없앤다. 라벨, 값, 컨트롤 상태로 이해되는 화면에는 설명 문장을 쓰지 않는다. 이해되지 않으면 문장을 더하지 말고 라벨과 배치를 고친다. 색과 상자도 지웠을 때 잃는 정보를 말할 수 있을 때만 남긴다.

이 스킬은 어떤 UI에도 적용되는 규칙만 담는다. 프로젝트에 디자인 문서가 있으면 함께 따른다.

규칙 번호 `S1`, `S2`…는 리뷰에서 인용하는 고정 식별자다. 삭제된 규칙의 번호는 빈 채로 두고, 새 규칙은 다음 번호를 받아 해당 절 끝에 둔다. 각 규칙은 캡처나 코드를 보고 예나 아니오로 판정한다.

## 설명 글

- **S1.** 화면에 상주하는 설명 문장은 0개다. 예외는 행동이 막혔거나 실패했을 때 그 자리에 보이는 한 줄뿐이다. 툴팁은 한 문장이고, 더 긴 설명은 사용 문서에 둔다.
- **S2.** 제목, 부제, 도움말 문단, 단계별 설명처럼 글이 쌓이는 구조를 쓰지 않는다. 제목 위의 대문자 소제목을 쓰지 않고, 대문자는 `ID`, `URL` 같은 약어에만 쓴다.
- **S3.** 빈 상태는 문장 한 줄과 버튼 두 개 이하다.
- **S4.** 면책·경고 문구도 상주시키지 않는다. 위험한 동작은 실행 직전의 확인 단계에서 한 줄로 알린다.
- **S5.** 컨트롤 라벨은 1~3단어의 명사나 동사다. 컨트롤 안에 문장을 넣지 않는다.
- **S6.** 화면 문구에 상투어, 인사말 같은 도입부, 챗봇식 문구를 쓰지 않는다.

## 색

- **S7.** 정상 상태는 기본 글자색으로 쓴다. 정상 응답, 일반 값, 완료된 단계에 의미 색을 칠하지 않는다.
- **S8.** 의미 색은 예외와 상태 변화에만 쓴다.
- **S9.** 포인트 색은 선택, 활성 상태, 핵심 행동에만 쓴다. Primary 버튼은 화면에 하나 이하다.
- **S10.** 그라데이션, 글로우, 배경 블러, 의미 없는 장식 색을 쓰지 않는다. 그림자는 팝업과 메뉴처럼 떠 있는 상자의 경계 그림자만 허용한다.

## 모양

- **S11.** 배경이나 테두리가 있는 상자(배지, pill, 칩)는 누를 수 있는 컨트롤에만 쓴다. 메서드, 상태 코드, 콘텐츠 타입, 개수 같은 데이터 값은 상자 없는 글자로 쓴다. 양 끝이 반원인 pill 모양은 쓰지 않는다.
- **S12.** 카드를 쓰지 않는다. 영역은 선으로 나눈 패널이다. 테두리로 나뉜 패널 안에 테두리와 여백을 가진 상자를 또 넣지 않는다. 팝업, 메뉴, 대화 상자만 떠 있는 상자다.
- **S13.** 도트는 상태나 범주를 나타내는 인디케이터에만 쓰고 항상 글자 옆에 둔다. 장식용 도트, 글자 없는 도트를 쓰지 않는다.
- **S14.** 이모지와 장식 아이콘을 쓰지 않는다. 대기 상태에서 깜빡이거나 숨 쉬거나 튀는 애니메이션을 쓰지 않는다. 계속되는 애니메이션은 진행 중인 작업 표시에만 쓴다.

## 정보와 배치

- **S15.** 같은 정보를 두 가지 표시로 반복하지 않는다. 예를 들어 실패를 색 띠와 색 글자로 두 번 표시하지 않는다.
- **S16.** 같은 숫자, 버튼, 라벨은 화면에 한 번만 보인다.
- **S17.** 온보딩 체크리스트, 번호 동그라미 단계, 히어로 영역, 아이콘·제목·설명으로 된 카드 묶음을 쓰지 않는다. 순서가 있는 설정은 컨트롤의 활성·비활성 상태와 막힌 이유 한 줄로 나타낸다.
- **S18.** 막대, 차트, 스파크라인은 값을 비교해야 할 때만 쓰고 숫자를 함께 보인다. 요약 카드처럼 이미 보이는 값을 다시 그리는 시각화를 만들지 않는다.
- **S19.** 자주 쓰지 않는 기능은 메뉴에 넣는다. 모든 기능을 같은 무게로 상단 바에 펼치지 않는다.

## PR 전 점검 절차

작성 agent와 리뷰 agent가 같은 절차를 따른다.

1. 요소를 더하기 전에 같은 정보를 이미 보이는 곳이 있는지 찾는다.
2. 데이터가 있는 상태와 빈 상태를 테스트 데이터로 캡처한다. 색이나 스타일을 바꿨다면 지원하는 테마를 모두 찍는다.
3. 캡처에 보이는 설명 문장을 모두 센다. 막힘·실패 때 보이는 한 줄도 센다. 라벨과 값만 빼며 기준은 0개다. (S1, S2, S4)
4. 아래 질문에 답한다. 모두 아니오여야 한다. 프로젝트 디자인 문서에 점검 질문이 있으면 함께 답한다.
   - 정상 행이나 정상 상태에 의미 색이 있는가? (S7, S8)
   - 데이터 값에 배경이나 테두리가 있는 상자나 pill이 있는가? (S11)
   - 카드, 패널 안의 테두리 상자, 글자 없는 도트가 있는가? (S12, S13)
   - 같은 정보가 두 번 보이는가? (S15, S16)
   - 바꾼 코드의 툴팁 문자열에 두 문장 이상인 것이 있는가? (S1)
   - 그림자, 그라데이션, 글로우가 있는가? (S10)
   - 이모지, 장식 아이콘, 대기 중 애니메이션이 있는가? (S14)
   - 30%를 지워도 잃는 정보가 없는 문구나 요소가 있는가? 있으면 지우고 다시 캡처한다.
5. PR 본문의 "UI 디자인 점검" 절에 설명 문장 수, 질문별 결과, 캡처를 적는다. 문장마다 S1의 예외 근거(무엇이 막혔거나 실패했는지)를 적는다.
6. 리뷰 agent는 PR 캡처로 3·4단계를 다시 확인한다. 적힌 근거로 문장마다 S1의 예외인지 확인한다. 위반은 규칙 번호를 인용해 코멘트하고 머지하지 않는다. UI를 바꾼 PR에 캡처가 없어도 머지하지 않는다.
