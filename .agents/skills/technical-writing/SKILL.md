# 기술 문서 작성

피곤한 엔지니어도 처음 읽을 때 이해하도록 쓴다.

- 역할이 없는 단어는 모두 덜어낸다.
- 짧고 일상적인 단어를 쓴다. "활용을 수행한다" 대신 "쓴다"라고 쓴다.
- 규칙 때문에 문장이 나빠지면 다른 방법으로 고치거나 그대로 둔다.
- 동의어나 풀어 쓴 설명 대신 실제 심볼, 파일, 플래그, 명령어 이름을 쓴다.
- 전문 용어를 새로 만들지 않는다. 개발자가 실제 대화에서 쓸 말을 쓴다. 이름이 있는 패턴은 처음 등장할 때 뜻을 설명한다.

## 문장 리듬을 조절한다

- 문장 길이를 섞는다. 두 가지 생각을 담은 문장은 나눈다. 하나의 생각을 담은 긴 문장은 유지한다.
- 설명 문서에서는 관점을 제시한다. 참조 문서는 담백하게 쓴다.
- 구체적으로 쓴다. "스키마 변경으로 문제가 생길 수 있다" 대신 "열 이름을 바꾸면 빌드가 실패한다"라고 쓴다.

## 먼저 문서 유형을 고른다 (Diátaxis)

문서 하나에는 유형 하나만 적용한다. 유형을 섞지 말고 문서를 나누어 링크로 연결한다.

- **튜토리얼: 직접 해 보며 배운다.** 독자가 무엇을 만들지 설명한다. 각 단계에서 눈으로 확인할 수 있는 결과를 만들고, 무엇이 보여야 하는지 알려 준다. 설명은 절 하나와 링크로 제한한다.
- **방법 안내서: 목표에 이르는 절차를 제공한다.** 독자의 문제를 해결한다. 기본 역량이 있다고 가정한다. 실행할 내용만 쓴다. 조건에 따라 경로를 나눌 수 있다. 제목은 수행할 작업으로 짓는다.
- **참조 문서: 찾아볼 사실을 제공한다.** 대상을 기술하는 데 집중한다. 담백하고 빠짐없이, 확실하게 쓴다. 문서 구조를 설명하는 대상의 구조에 맞춘다.
- **설명 문서: 이해와 이유를 다룬다.** 범위를 한 주제로 제한한다. 설계 결정, 역사, 제약, 대안이라는 맥락을 제공한다. 의견은 이 유형에서만 허용한다.

## 독자에게 직접 말한다 (Google 개발자 문체)

- 독자가 할 일을 직접 설명하고 현재 시제로 쓴다. "사용자는 설정해야 합니다"보다 "설정하세요"라고 쓴다. 독자를 "당신"으로 반복해서 부르지 않는다.
- 누가 무엇을 하는지 밝힌다. 행위자를 알 수 없거나 중요하지 않을 때만 피동문을 쓴다.
- 지침은 명령문으로 쓴다. 조건은 지침보다 먼저, 일반적인 경우는 예외보다 먼저 설명한다.
- 유행어, 비유, 의례적인 "부탁드립니다"를 쓰지 않는다. 절차에서 "그냥", "쉽게", "빠르게"라고 말하지 않는다.
- 앞으로 설명할 내용을 미리 예고하지 않는다. 연속된 문장을 같은 표현으로 시작하지 않는다.
- 링크 문구로 연결되는 곳을 설명한다.
- 제목에 요점을 담고 자연스러운 한국어로 쓴다. 불필요한 기호나 영문 대문자로 꾸미지 않는다. 페이지마다 `h1`은 하나만 두고 제목 단계를 건너뛰지 않는다.
- 순서가 있는 절차에는 번호 목록을, 나머지에는 글머리표를 쓴다. 완전한 문장으로 목록을 소개한다. 항목들의 문법 구조를 맞춘다.
- 코드는 코드 서식으로, UI 요소는 굵게 표시한다. 쉼표와 접속 표현으로 나열된 항목의 경계를 명확하게 한다. "등등"으로 목록을 얼버무리지 않는다.

## 한 번에 하나의 내용을 전달한다 (STE 규칙)

- 문장 하나에 지침 하나만 담는다. 그 밖의 문장에도 생각 하나만 담는다.
- 동작이 여러 개이거나 조건과 수식절이 길게 이어져 되읽어야 하는 문장은 나눈다. 한 가지 생각을 자연스럽게 전달하는 문장은 길이만으로 자르지 않는다.
- 경고나 조건은 해당 단계보다 먼저 쓴다.
- 대상을 구분하는 조사와 문장 성분을 생략하지 않는다. "서버 클라이언트 인증서 검증" 대신 "서버가 클라이언트 인증서를 검증한다"라고 쓴다.
- 단어 하나에 의미 하나를 부여한다. 같은 동작에는 같은 단어를 쓴다.
- 절차는 직접적인 명령문으로 쓴다. 서술문이나 피동문으로 쓰지 않는다.
- "~하면서", "~하는 것으로" 같은 연결 표현을 불필요하게 늘이지 않는다. 동작 사이의 순서나 인과관계를 분명히 쓴다.

## 두 가지로 해석될 여지를 없앤다 (Global English)

- "만", "아니다"처럼 범위나 부정을 나타내는 말은 수식하는 대상 가까이에 둔다.
- 명사를 길게 나열하지 말고 관계를 풀어 쓴다.
- "그것", "그들", "이것"이 가리키는 대상을 하나로 명확하게 한다. "이는"이나 "이러한"으로 앞 절 전체를 막연하게 받지 않는다.
- 서술어와 문장 구조를 나타내는 조사·어미를 생략하지 않는다.
- 나열된 대상이 혼동되면 각 대상에 조사를 붙인다. "그리고"나 "또는"이 연결하는 범위를 밝힌다.
- 세미콜론이나 줄표 대신 마침표를 쓴다. 슬래시로 선택 관계를 표현하거나 단복수를 괄호로 병기하지 않는다. 괄호 속 설명도 문법적으로 완결된 단위로 쓴다. 실제 경로와 코드의 기호는 보존한다.
- 같은 대상은 어디서나 같은 이름으로 부른다.
- 관용구, 지나친 구어체, 설명 없는 약어, 비유를 피한다.

## 문체와 저장소 규칙

- 이 스킬이 다루는 모든 문서에 **unslop** 스킬을 적용한다. AI 특유의 어휘, 군더더기, 유보 표현, 형식적 특징의 목록은 그 스킬에서 관리한다.
- PR 설명과 커밋 메시지도 글이다. Diátaxis를 제외한 모든 규칙을 적용한다. PR 본문은 리뷰어가 1분 안에 읽을 수 있는 브리핑으로 쓴다. 병렬 에이전트 작업 로그, SHA 목록, 측정값 표를 붙여 넣지 말고 링크로 연결한다.
- 제품 UI 문구는 문서가 아니다. 제품의 문구 작성 지침을 따른다.
- 코드 예시는 탭으로 들여쓴다. 실제 경로를 쓴다. 개수나 디렉터리 트리에 관한 주장은 해당 변경이 반영되는 커밋에서 사실이어야 한다. 결과를 다시 생성하는 명령어도 함께 적는다.
